## 取图链路和实验发现

`src/host/standalone-window.ts` 使用本机 Chrome（没有时 Edge）以 `--app` 模式承载独立页，并不是 DSH Electron 的原生子窗口。`standalone-assets.ts` 声明 ICO、PNG 和 SVG favicon。

本次先从隔离 DSH 0.2.2-rc.3 的正常按钮打开，重现现行图标。随后用同一 Chrome 157.0.8103.79、独立测试资料、相同启动方式及 favicon 声明建立最小复现，排除笔记业务影响。

| 实验 | 原生 32 px 对直接源图的平均像素差 | 结论 |
| --- | ---: | --- |
| 现有 ICO + PNG + SVG 声明 | 8.22 | 缓存的 16/32 px 均与源文件一致，窗口图标仍有柔化 |
| 补齐 20/24/30/36 等 ICO 帧 | 9.24 | 此链路没有因补帧而改善 |
| 仅 PNG32 | 8.81 | 仍有柔化 |
| 仅 PNG64 | 9.22 | 仍有柔化 |
| 仅 SVG | 9.24 | 仍有柔化 |
| 暂时直接给原生窗口提供 32 px 图标 | 0.00 | 原生提取保留源像素；不是正式接入 |

差值比较预乘 alpha 后 RGBA 通道，范围 0–255，越低越接近，不是主观质量评分。现行输出与源 16 px 用 Lanczos 放大到 32 px 的差值仅 1.42，比直接源 32 px 更接近，结合缓存和各格式试验，支持「窗口使用小 favicon 后再放大」这一判断；未用这些数字宣称已逐行追踪 Chrome 内部执行。

临时原生赋值只针对测试窗口，同时提供窗口大、小图标，截图后恢复原句柄并释放新句柄；没有修改 Chrome、DSH 或插件的正式代码。仅改变大图标并不能保证任务栏不用原来的小图标，因此最终实屏采用两者一起提供的实验。清晰度正式修复需另行规划：核对窗口身份、处理刷新与重开、释放图标、按实际 DPI 取图及验证退回机制。不建议为图标改为另一整套窗口架构，也不建议未经证据持续加大源图尺寸。

微软说明 Windows 会在目标尺寸不匹配时缩放；这是一般机制，不能直接据此断定本案补帧就能解决。[官方尺寸说明](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-construction)。Chromium 当前源码的非普通窗口路径会读取当前页图标；该源码为当前主分支参考，并非已核对本机版本的全部源码。[BrowserView](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/views/frame/browser_view.cc)。本案以实际版本实验为主要依据。
