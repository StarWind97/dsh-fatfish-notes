## 3. 已经确定的产品规则

- 纯个人笔记产品，只使用用户自己的专用 GitHub 私有仓库。社区与公开链接分享不再属于本项目，不重新引入。
- 首次初始化必须联网绑定专用私库；绑定后临时断网仍能编辑和保存，恢复后同步。普通用户不应被技术细节和频繁操作提示干扰。
- Markdown 是正文；笔记本是组织归属，不改为与 Obsidian 共用同一份内部仓库。PDF、音视频等普通附件保存、同步、下载和导出，不提供播放器或通用预览。
- 阅读态与编辑态分开。编辑期间保存本机草稿，完成编辑或离开笔记后生成正式修订并同步；取消丢弃本次草稿。意外退出的持久草稿按恢复规则处理，不能退回“每次停笔都生成正式版本，取消再创建恢复版本”的旧方案。
- 本机不同窗口编辑同一篇笔记受编辑资格保护；不同篇可分别编辑。不能为了性能跳过身份、路径、内容完整性和跨窗口编辑校验。
- 同库笔记本名称不能重复；默认本和工作区默认本不是同一个概念。笔记可更换归属，一个笔记本可作为多个工作区的默认保存位置。
- 一个笔记可关联多个会话。侧栏新建及从当前会话转存的笔记自动关联当前会话；“从本会话保存”是关联列表内的过滤条件。
- 会话转存先展示选材和保存选项。标题必填，摘要与标签选填；AI 建议先生成到可编辑表单，再由用户保存，不能污染当前会话问答。正文仍由用户手动编辑。
- “引用到当前会话”支持单篇、多选及多次追加。当前采用宿主材料副本加输入框说明，让 Agent 读取全文和文件，不等同于原生附件栏接入。正文所引用材料必带；补充附件可选择。去重仅针对当前未发送输入中的同一版本；发送后允许再次引用。
- 正文中的图片或文件链接与补充附件是两种归属。材料移入正文后退出补充区；后来从正文删除引用，不自动回流补充区。补充区是额外材料，不应重复展示正文已经使用的文件。
- 常见操作的界面应紧凑、直观、保持同一套图标语言。小操作使用有悬浮提示的对号/叉号；不是所有动作都需要大弹窗。
- 兼顾必要性、实现维护成本和外观，优先常见使用情形，避免为少见边界提前搭建复杂体系。

上面是接续要点，完整行为以产品设计和相应最新专项为准。旧文档中带历史版本或日期的段落不代表当前实现。

## 6. 未解决项：文件添加等待

### 已有实测

同一隔离 DSH，1660 × 1100 窗口；各组五次，单位毫秒。原始数据与环境说明在最新交付记录。

| 输入与完成条件 | 五次结果 | 中位 / 最大 |
| --- | --- | --- |
| PNG + 文本，总计 140 B；两项插入且进度结束 | 877、895、600、646、605 | 646 / 895 |
| JPEG + 文本，总计 51,171 B；照片预览完成，首轮未固定前台 | 11425、2945、3126、2995、2761 | 2995 / 11425 |
| 同一照片 + 文本，明确置前后复测，照片预览完成 | 6968、5496、6049、9792、2702 | 6049 / 9792 |

前台复测中，正文插入耗时为 6961、5488、6038、9780、2689 ms，照片预览仅晚 7–14 ms。没有证据支持把主要等待归因于图片解码；也不能简单说是后台窗口节流、电脑速度或 GitHub 网络慢。

请求记录显示：本机草稿请求部分超过一秒；每个文件的开始、分块、完成通常串行，许多请求各约 0.5–1.6 秒；Worker 脚本请求约 49–89 ms。这些是请求完成时间，**尚未拆分为转发、排队、校验和磁盘处理各自的时间**。

### 接下来调查的线索（尚非根因结论）

1. [routes.ts](../../src/host/routes.ts) 中，包含 `/notes/draft`、`/notes/transfer` 的保护路由会先等待 `workspaceRequest('/workspace/state', {})`。
2. [application.ts](../../src/host/application.ts) 中 `workspaceRequest` 进入 `notes.repository.coordinate`。
3. [repository.ts](../../src/notes/repository.ts) 中 `coordinate` 使用仓库公共队列；需要测量其他读写/轮询/同步是否造成排队，及每次扫描或校验耗时。
4. [note-transfers.ts](../../src/host/note-transfers.ts) 中文件传输生命周期、仓库读取及客户端逐文件往返值得分段计时。
5. 在保持输入规模、资料、前台状态一致的条件下，明确“点击/粘贴 → 本机草稿就绪 → 请求发送/接收 → 文件完成 → 正文插入 → 图片显示”各阶段。

优先消除实际测出的重复等待，不先推翻保存机制。保护检查可以研究如何减少重复工作，但不能直接删除或绕过。现在没有足够依据承诺最终会降到多少毫秒；完成拆分后再提出目标和最小方案，经用户确认开发。

现有基线足够支持继续诊断，无需仅为交接再跑五次。涉及保存/缓存/同步的优化按第三档验证；普通局部接收行为按第二档。发布前按第三档和实际安装要求验收。

页面操作要点：

- 先明确选择体验笔记，再输入；不能假设当前页仍是脚本上次打开的笔记。
