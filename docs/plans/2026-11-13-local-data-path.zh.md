## 问题与目标

基线为 main `ad4d4d7`，工作区干净，上一轮[同步资源交付](2026-11-13-sync-resources-results.zh.md)已完成。当前小文件同步繁忙显示中位 1472 ms、最大 2041 ms（5 次），同步安装中位 792 ms。阶段达标不能当作产品性能充分达标。

确认的结构问题：`load()` 在缓存命中前扫描全库；小文件接收还计算整个 manifest；窗口状态预检与仓库长操作排同一条队列；同步远端读取仍重复处理完整历史与资源。前轮两小文件共 51171 B，仅接收中的两次目录扫描合计 331–468 ms，状态预检本身不足 1 ms 却曾等待约 600 ms。各阶段可能交错，不相加推算总耗时。

目标是让常用本机操作主要承担当前笔记和当前文件的成本，保持保存、取消、并发编辑、共享资源清理和同步确认的正确性。建议性能验收目标：同一小文件组合热态显示中位不超过 500 ms，繁忙场景 p95 不超过 1000 ms；这是待验证目标，不能预先承诺。每种主要场景至少 30 次，报告中位、p95、最大值及全部样本。首开与热态分开，首开不足 5 次须注明。

## 范围与方案选择

选择保留 TypeScript / Node / Electron、Markdown / JSON / Git 格式，整顿数据访问和调度。候选比较：

| 方案 | 收益与代价 | 决定 |
| --- | --- | --- |
| 继续逐处增加缓存与缩小批次 | 改动小，但局部操作仍依赖全库规模 | 仅用作对照，不作为完成标准 |
| 可重建索引、按相关对象校验、缩短提交与身份检查的等待 | 解决重复遍历和过大排队范围；须验证失效、外部修改和恢复 | 本轮选择，分步试验后实施 |
| 迁移 SQLite 或换技术栈 | 涉及迁移、双份状态和新运行约束，当前没有充分必要性证据 | 不在本轮实施 |

不修改存储协议、现有数据格式、同步频率、用户资料位置、身份与可见性规则、HTTP 栅栏。不通过删除完整性校验、弱化并发保护、伪报保存成功或只有界面先显示来满足耗时指标。若需要数据库迁移、宿主配置或改变这些默认行为，另行提出具体方案。

## 执行阶段

1. **固定基线与试验边界。** 保存当前源码/安装包对照，使用原隔离资料和 100 / 1000 篇受控资料副本；记录历史修订、资源和文件数。先测库读取、局部文件接收、同步繁忙和队列等待，区分真实宿主与直接接口；沿用原生粘贴脚本，扩展样本，不重做无关 E 功能。
2. **本机索引试验。** 索引可从正式文件重建，只记录已校验状态和变化。自身写入明确更新或使相关条目失效；外部变化提示、目标文件直接核对、初始化/异常完整重建相互补充。不能只依赖监听，也不能复用已经变化的文件。先比较原实现与试验的扫描次数、耗时和故障行为，再选择正式实现。
3. **局部操作与调度。** 小文件接收核对当前草稿、笔记、编辑资格及资源，不为尚未产生正式修订的接收重算全库清单。审查路由身份预检与真正写入的重复排队；纯状态读取与长 I/O 分离，真正写入时仍原子核对资格、资料根和当前修订。读取从一致的已提交状态取得数据；不得看到中间合并或迟到写入。
4. **增量同步试验及整合。** 利用已验证的 Git 对象身份，限定同一仓库/校验版本下复用不变对象，变化时重新读取校验。网络身份核验继续执行，损坏、删除、换库、并发写入和推送重试仍按原规则处理。内存和失效边界必须有上限；不把「同名文件存在」等同于安全。
5. **验证、调整与交付。** 每步用受影响专项检查反馈；收益不足或产生额外复杂度时记录原因并调整，不保留没有被验证的试验实现。稳定后类型检查、构建、全量回归，安装到原隔离入口，实际验证保存/取消/双窗口/同步/下载/重启与同条件性能。完成文档、正常提交与远端 SHA 核对，不创建发布。
