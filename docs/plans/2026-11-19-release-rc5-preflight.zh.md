## 验证与交付

1. 核对实际 Windows 宿主、安装路径、`dsh://` 注册目标和隔离资料归属。桌面使用本机官方 rc.5 程序，宿主资料和 Electron 窗口资料使用项目内隔离路径。Web 使用固定版本的独立运行时。通过定向自动化操作测试窗口，按归属收尾测试进程。
2. 以发布包摘要核对公开 0.9.2。复核 0.9.1 在 rc.5 被拦截、0.9.2 在同版本可通过实际安装与使用。在指定测试私库验已有笔记、主界面、独立窗口、会话侧栏、保存、跨窗口显示、同步与重启读回。
3. 运行类型检查、构建和全量回归。打包到项目忽略目录，核对包清单与安装文件，从 0.9.2 升级到同一个新版候选。在 rc.5 Desktop、Web 检查已有笔记、搜索组合条件、正文定位、会话转存、保存、同步与重启，并保留 rc.4 Web 的对照结果。性能采用同资料对照普通笔记、长文、切换笔记本和保存跨窗口刷新，热操作至少 5 次。
4. 用同一候选包核对固定名 `dsh-fatfish-notes.tgz` 和带版本下载包的摘要一致。在隔离环境验证市场根据旧安装链接发现新版、选择正确的正式标签与完整包。市场条目切换前，先确认新正式版已有固定名资产。切换后核对用户使用的实际目录索引；以前发布的固定版本下载继续供回退。依据为[市场提交指南](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/contributing.md)和[应用内更新逻辑](https://github.com/dsh-market/dsh-market/blob/main/src/release-updates.ts)。
5. 对照候选检查随包手册、在线说明及当版截图，记录需调整的章节和理由，按[用户文档更新约定](../demo-content.zh.md#发布前更新用户文档)讨论后再改。交付本轮兼容矩阵、可复验候选、市场切换草案和待确认事项。预计一轮构建回归、一轮实际宿主验收和一轮市场演练。

实际宿主侧若遇到接口变更，按公开接口、实测症状及用户价值记录，并复核会话搜索结果转存和原生附件公共链路。缺少真实证据的组合保留待验。若候选有回归，保留正式 0.9.2 作为隔离资料的重装回退包；若市场出现问题，恢复条目的固定版本入口。隔离证据归入 `.dsh-home/pure-001/release-rc5-preflight/`。
