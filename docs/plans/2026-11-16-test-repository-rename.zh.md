## 为什么不能只改 GitHub 名称

`src/private-workspace/sync.ts` 的 `validateRemote()` 同时核对私有性、仓库/拥有者 ID、拥有者登录名和仓库名称，配置位于活动资料的 `backup/sync.json`。仓库改名后，旧绑定仍会拒绝名称不匹配。普通换库流程也会拒绝把同一 ID 当新库，不能借此绕过改名维护。

`src/git/backend.ts` 按规范化仓库名称计算专用缓存目录，并核对 `.git/dsh-owner.json` 与 origin；不得把旧缓存的来源记录直接改成新名称。应由现有后端针对新名称创建独立缓存，旧缓存保留以供回退。笔记目录和清单以稳定 ID 校验，原则上可保持，但必须实际验证，不能只凭 GitHub 重定向推断可用。

官方背景：[GitHub 仓库改名](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)。网页及 Git 地址重定向不是本插件身份校验的替代品。

## 验证、风险与回退

这是同步身份维护，按第三档处理：类型检查、构建、全量回归，真实指定私库的改名后身份/读写/恢复验证；本机只读检查不能替代真实同步。没有必要为改名新增用户功能或包版本，但安装内容若发生变化需重新验证。

风险包括名称已占用、绑定未全部更新、启动时旧进程继续写入，以及把新地址误认为另一仓库。缓解依靠稳定 ID、停进程、单 profile 原子更新、原缓存保留及完整备份。

失败回退：再次确认仓库 ID，停止测试进程；将同一仓库恢复原名，核对私有性和 main SHA，恢复原绑定并复用保留的原缓存。不得删除或重建远端仓库，不强推，不清空笔记。新缓存单独保留待核查；回退后重新检查读取与同步状态。

预计一轮独立维护与真实同步验收，耗时取决于远端同步和新缓存获取。交付应含前后身份/SHA/数据清单对照、实际验证、回退记录及隔离入口；不与导航修正或 Logo 选择捆绑批准。
