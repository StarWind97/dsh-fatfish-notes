## 结论

**推荐路径已在当前 Windows Desktop 验证可行：将选中的材料保存为 DSH 附件副本，使用公开输入接口插入文件引用和简短读取说明，由用户检查并发送。** 无需另建工作区中转文件夹，不依赖笔记原文件长期保持在同一位置。

这属于“引用到当前会话”，不是原生输入框附件登记。两轮模型读取时，输入框附件数始终为 0；DSH 正常解析文件引用，模型实际调用读取工具。第一轮 E0 发现的公共图片上传错误没有被修复；本次走的是宿主附件服务保存文件的另一条公开路径。

## 模型实际读取证据

环境为 Windows / Node 24.21.0 / DSH Desktop 0.2.2-rc.1，宿主选择 DeepSeek-V4.1-Flash。仅使用项目内隔离资料和合成材料，按已有授权发送了 2 轮只读测试，没有发送用户笔记。

图中没有文字，Markdown 图注只有“示意图”，提示词不含答案。

- 第一轮正确回答：正文核对词“青岚-4827”；CSV 的 birch 为 `38 / LM-7319`；紫色三角形有 4 个白点、蓝色区域里是黄色实心圆、左下有 3 根橙色竖条。
- 第二轮在重启、原文件移走及会话移入未分组后，换问另一组细节：maple 为 `24 / VT-06`；绿色长方形有 5 个白点、红色圆形内是白色十字、右下黄色图形为空心圆环。均正确。
- 两轮会话事件都记录了重新读取 Markdown、CSV 和 PNG 的工具调用，不是仅复述上一轮答案。模型没有调用写入工具；测试工作目录仍为空，保存副本摘要保持不变。

界面显示每轮约 12 秒，包含模型推理和工具操作；这只是 2 次小材料功能验证，**不是正式引用操作的性能基准**，不据此承诺长文、大文件的响应速度。

## 位置和接口

普通文件通过 `ctx.attachments.saveFile` 保存，`fileHostPath` 返回当前本机宿主可读路径。本次路径为：

```text
<DSH_HOME>/attachments/v1/files/<摘要前缀>/<SHA-256>/<文件名>
```

DSH 统一管理附件对象，会话记录另行保存。插件不手工拼接或写入上述内部目录；只调用公共保存和读取方法。Markdown 中图片和附件链接改为本次副本路径，随后通过 `captureInsertion → insertText → persistDraft` 加入当前输入。关闭后草稿、会话记录和附件副本均保留。

工作区和未分组决定会话如何组织，不要求两套附件保存逻辑。无需在每个工作区创建 `.fatfish-notes` 等目录。用户移动笔记库或修改笔记后，已经引用的材料应保持当时内容，不自动跟着变动。

本次仅验证本机执行环境；WSL、远程执行和其他文件系统映射未验证，不能直接把 Windows 宿主路径用于这些环境。正式开发应先核对执行环境和可读路径，不可用时明确提示。模型读图仍取决于当前模型及工具能力。

全新的未分组空会话在当前宿主显示“选择一个工作区开始”，没有正常输入框。后续入口应以有效会话和可用输入框为条件，沿用宿主开始会话的流程；不能承诺在尚未开始的任意空白页插入。已开始会话移入未分组后的使用已实测。

## 对 E 方案的建议，待确认

保留原 E1 侧栏与来源笔记、E2 手动关联。建议在整体验收前增加“引用到当前会话”：

1. 从会话侧栏选择一篇笔记，先完成现有自动保存，再读取一个确定版本。
2. 正文、所用图片和普通附件保存为宿主副本；仅处理用户选中的笔记及其合法附件，不扫描工作区或把全部私人库交给模型。首次以单篇为范围。
3. 输入框加入文件引用与简短读取说明，保留用户已有文字，供继续提问；由用户发送，不自动执行模型任务。只做材料准备，不恢复“AI 整理正文”。
4. 界面明确区分“关联，便于查找”与“引用，准备交给当前会话使用”；不用“已附加”描述没有进入原生附件栏的结果。
5. 复用宿主存储，不增加工作区目录、第二套同步或独立垃圾回收机制。现阶段不要求会话附件跨设备同步；长期清理沿用宿主能力，不直接删除宿主内部对象。

真正的原生附件登记继续留作接口待办。引用能力可复用 E1 的选择入口，但需要服务端快照准备、合法路径/附件校验、输入状态保护、体积限制和真实宿主验收，工作量为小到中等，不能将探针按钮直接作为正式功能交付。

用户确认纳入后，再更新[E 专项实施方案](2026-11-10-stage-e-implementation.zh.md)的步骤、影响面、回退和验收。正式开发需覆盖失败/取消、重复点击、切换会话、保留已有原生附件、中文输入，以及大材料准备进度；此次小样本不替代这些验收。
