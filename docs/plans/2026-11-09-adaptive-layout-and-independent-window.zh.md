# 自适应三栏与独立窗口正式规划

状态：**2026-11-10，主规划阶段 A 的 A1—A5 已完成开发与隔离验收，等待用户审核体验。** 用户确认布局后要求连续做到 A 完成，已统一交付[阶段 A 结果](2026-11-10-stage-a-results.zh.md)。A1/A2 的样稿与验证保留为前序证据；本轮未正式发布。

本文是[主规划](2026-11-09-product-iteration-roadmap.zh.md)**阶段 A 的专项实施方案**，负责详细规则、影响范围、A1—A5 交付物与验收；总体顺序、当前阶段及下一步以主规划为准。阶段 A 之后依次为 B 查找、C 整理与恢复、D 关联与复用（原 E），完成统一验收并经用户确认后集中发布，再进入 E 会话复用（原 D）、F AI 输出。A5 为内部验收节点，不单独正式发布。

基线：肥鱼笔记 0.7.0、Windows / DSH 0.2.2-rc.1。已有[独立窗口验证](2026-11-09-independent-window-validation.zh.md)证明同一服务上的浏览器应用窗口可行；该记录属于前期原型，后续 A1 补验及正式功能的完成状态以阶段 A 结果为准。下列章节保留已批准的设计和验收规则。

## 1. 目标与范围

让用户在 DSH 内方便管理笔记，也能独立打开笔记窗口，继续在 DSH 会话中工作。两种窗口共用界面、笔记服务和资料，通过可用宽度调整布局，并避免同一篇笔记被两个窗口同时修改。

本批包含：自适应三栏、笔记本导航与折叠、独立窗口入口与重用、本机内容更新、主题跟随、编辑占用与交接、关闭及重启后的保存与连接提示。

本批不包含：会话相关笔记侧栏、AI 正文功能、自由多窗口系统、多人协作、跨设备编辑锁、新存储模型、修改 DSH 安装文件。右侧未来操作面板只预留布局方向，不预建功能框架。继续只使用一个专用私有仓库和一个负责写入的 DSH 笔记服务。

## 2. 已确认的界面规则

### 2.1 按可用宽度决定布局

宿主内和独立窗口使用同一套布局规则；不以「是否全屏」或「是否独立窗口」作为三栏开关。测量笔记插件自己的内容区域，扣除 DSH 侧栏等占用。

| 情况 | 默认行为 |
| --- | --- |
| 空间充足、没有手动偏好 | 展开「笔记本列表 → 笔记列表 → 阅读/编辑」三栏。 |
| 空间不足 | 收起笔记本列表，在笔记列表顶部用下拉框选择笔记本；正文优先保留可读宽度。 |
| 用户手动收起笔记本列表 | 记住选择，不因小幅拉宽窗口就重新展开；用户可主动展开。 |
| 用户希望展开，但窗口暂时过窄 | 临时采用下拉框，不覆盖手动偏好；恢复足够空间时再恢复展开。 |
| 目录等辅助区域展开 | 根据剩余宽度调整或收起辅助栏，保留现有目录的宽窄模式，避免把正文压成窄条。 |

笔记本栏和笔记列表均可在合理范围内调宽，宽屏时不按比例无限扩张。断点、初始宽度、调整范围和正文最小宽度在 A1 样稿中确定，以实际文字与操作空间验收，不在规划中先锁死数字。拖动窗口时避免临界宽度反复展开、收起。

笔记本栏提供全部笔记、各笔记本及管理入口；下拉框与栏内选择保持一致。现有默认笔记本规则、笔记本管理选项卡、列表摘要、回收站、排序和筛选继续复用，避免新增重复管理体系。

宽度和展开偏好保存在本机，按宿主内、独立窗口分别记忆；不因设备尺寸差异随 GitHub 同步。正文标准宽度/全宽选择及现有目录功能继续有效。未来右侧操作面板与目录共享辅助空间，本批不实现该面板。

### 2.2 独立窗口与宿主内入口并存

- 笔记顶栏提供「独立窗口打开」。打开时保留当前笔记；有编辑时先完成保存，再把当前笔记交给目标窗口显示，不依赖窗口失焦碰巧触发保存。
- 首期只允许一个独立笔记窗口。重复点击应唤回已有窗口，不不断新建窗口。若独立窗口正在编辑其他笔记，不强制切走，保留其内容并提供切换选择。
- DSH 内的笔记界面仍能打开，两处都可阅读、搜索、切换、导出、新建，也可编辑不同笔记。独立窗口不导致主界面整体只读。
- 会话中的「保存到笔记」与会话导出保持可用；保存新笔记不要求关闭独立窗口，也不自动把 DSH 主窗口切离会话。
- 两处阅读内容和列表及时更新，但不能用另一窗口或云端的新内容覆盖正在输入的正文。

## 3. 同篇笔记只允许一处编辑

### 3.1 用户看到的行为

| 操作 | 行为 |
| --- | --- |
| 两边同时阅读同一篇 | 都可操作阅读、目录与导出；保存后的内容在另一处更新。 |
| 一处进入编辑，另一处仍阅读 | 阅读处轻量提示「正在独立窗口中编辑」或「正在 DSH 主窗口中编辑」，不弹出阻断阅读的对话框。 |
| 另一处点击编辑 | 提供「在这里继续编辑」；先完成交接，成功后进入编辑态。 |
| 两处同时请求编辑 | 服务端只允许其中一处获得编辑资格，另一处保持阅读，不产生两个可写编辑器。 |
| 编辑不同笔记 | 两处均可编辑，沿用自动保存。 |
| 完成编辑、切换笔记或正常关闭 | 保存完成后释放占用；关闭过程由恢复机制兜底，不能仅凭页面消失就宣称已保存。 |
| 窗口异常关闭或失去连接 | 不永久锁住笔记；恢复连接后重新核对编辑资格和最新版本，旧窗口不能继续提交过期内容。 |

保护覆盖标题、标签、摘要、正文、归属笔记本、附件引用，以及移入回收站、恢复和彻底删除。另一窗口不能通过菜单、批量操作或其他接口绕过限制。

批量动作涉及被另一窗口占用的笔记时，先说明受影响数量并暂不执行整批，不悄悄漏掉部分项目。移除笔记本等会影响其中笔记的操作也做同样检查。仓库切换、重置和搬迁先协调两处编辑与保存，再沿用现有规则，不允许在旧资料上继续写入。

### 3.2 编辑交接顺序

1. 当前窗口请求在这里继续编辑，暂时保持阅读态。
2. 原编辑窗口等待正在进行的中文组词或附件处理结束，再短暂暂停新输入并完成剩余保存；允许取消交接，不截断输入。
3. 原窗口确认保存成功后退出编辑；服务端撤销原编辑资格。
4. 目标窗口获得新的编辑资格，读取最新修订，进入编辑态。

保存失败、连接断开或原窗口无响应时，不能直接抢占并覆盖。提示简短原因，保留原稿和当前阅读状态；正常交接不额外要求重复确认。异常恢复沿用版本核对和必要时保留副本，不把冲突副本当作日常双窗口操作流程。

### 3.3 服务端协调的最小实现

两种界面使用不同浏览器环境，不能把浏览器本地存储或页面间广播当作唯一协调者。由同一个笔记服务按「仓库身份＋笔记 ID」管理短期编辑占用。

- 每个窗口有独立身份，获取、续期、释放或交接编辑资格；占用状态仅在本机运行期维护，不写进同步仓库。
- 每次已有笔记的修改都核对当前编辑资格和修订版本；修改检查与写入进入同一串行流程，防止交接期间已经排队的旧请求继续落盘。失效窗口的写入明确拒绝。
- 新建笔记、会话转存、导入新笔记不全局受限；现有模型元数据任务和其他修改已有笔记的入口须遵守同一保护，不能从后台覆盖用户编辑。
- 完成编辑正常释放；异常失联通过有限存续期回收。旧窗口恢复时重新申请并读取最新内容，不自动重放过期写入。续期频率和超时以后台窗口、系统休眠实测确定，不追求复杂分布式锁。
- 现有 `expectedHeads` 版本校验仍保留。跨设备同步引入的变更继续使用既有冲突规则，不承诺跨设备实时编辑互斥，也不阻塞正常远端同步。

此机制与当前防止两个 DSH 服务写同一目录的写入者锁分工不同；两者均保留。

## 4. 独立窗口运行与保存边界

### 4.1 技术方案取舍

| 选择 | 结论 |
| --- | --- |
| 两种窗口共用自适应三栏 | 采用。布局复用现有 React/CodeMirror，必要性明确，不改变内容模型。 |
| 只允许独立窗口使用三栏 | 不采用。宿主内有足够空间时同样应利用。 |
| 独立窗口打开后禁用宿主内全部写入 | 不采用。限制按篇执行，保留其他笔记和会话采集。 |
| 同篇两边随意编辑，事后保留冲突副本 | 不作为正常方案。仅保留既有异常与跨设备冲突保护。 |
| 浏览器应用窗口调用原 DSH 服务 | 首选正式路线；独立前端入口复用现有组件与接口。Windows 检测可用 Chrome/Edge，不修改默认浏览器或安全设置；Edge 尚需实测。 |
| 改动 DSH 的 Electron 安装文件或新开一个写入服务 | 不采用。公共接口与单一服务是本批边界。 |

新增窗口打开请求只能启动插件自己的页面；不接受任意程序路径、命令或网址。保留现有 loopback、Host、Origin、sec-fetch-site 与仓库身份检查，不搬运账号 Cookie 或凭据。窗口登记与主题状态通过插件自己的受控接口传递。

### 4.2 本机刷新、主题与保存

本机窗口间更新与 GitHub 同步分开。已有原型证明 5 秒一次本机读取可用；正式实现优先复用轻量状态查询，携带变化标记，有变动才刷新列表或阅读内容，不每次轮询都重载整篇。编辑期间只更新必要状态，不替换正文。只有实际笔记保存等既有事件触发云端同步，布局、占用续期和阅读刷新不触发 Git 提交。

两处使用相同的深浅色样式。宿主内监听实际生效主题，向本机服务共享，独立窗口订阅；宿主选择「跟随系统」时跟随最终生效主题。不得只复制启动时的颜色快照。独立窗口没有另设一套冲突的主题偏好。

沿用无需用户关心保存的体验：停笔自动保存，离开时提交，返回后默认阅读最新内容；手动完成编辑等同于确认保存并回到阅读。编辑占用的释放以保存和状态确认来决定，不仅依赖 `blur`。

### 4.3 A1 补验问题与接续约束

前次验证未解决以下问题。本轮的真实结果、最小协调契约与限制见 [A1 记录](2026-11-09-a1-layout-window-results.zh.md)；稳定入口、窗口重用和重启恢复已完成原型验证，正式编辑保护、主题跟随等仍待后续实施，不能把样稿当成完整能力：

1. **窗口重用及唤回**：在不修改宿主安装、不向用户常开调试端口的前提下，实现同一独立窗口的识别、重用和当前笔记传递；验证 Chrome 与候选 Edge 的真实行为。
2. **DSH 退出及重新连接**：DSH 服务停止时，窗口显示「DSH 已关闭，请重新打开后继续」，暂停写入；旧的「已同步」提示不能继续造成误解。完整退出时不另留一个隐形笔记服务。
3. **地址变化下的恢复**：当前服务重启会换端口，浏览器恢复记录按来源隔离。需要明确稳定入口或本机恢复记录的衔接方式，保证正常关闭和重启后能找到最新保存及未完成内容；不得仅把旧窗口导航到新地址而遗失恢复记录。
4. **旧恢复记录与编辑占用**：恢复必须先核对仓库、最新版本及编辑资格。不同窗口的草稿分开保存，不能共用一个恢复槽互相覆盖；已经过期的原稿不能静默覆盖后来内容。

A1 比较最小方案并实际验证，明确未完成输入能保证到什么程度。目标是覆盖正常退出、刷新和服务重启，不承诺断电前尚未持久化的每个按键。若必须增加独立常驻代理、修改宿主或其他超出上述边界的方案，停下向用户解释并重新确认，不自行扩展架构。此项未通过前，不开放独立窗口正式写入，也不进入对外发布验收。

若验证发现独立窗口的实现和维护成本明显超出收益，提出缩减或延后窗口、先交付共享布局等选择，待用户决定后同步调整主规划及本专项；不自行改变阶段顺序，也不让未收敛的窗口方案长期阻塞后续基础功能。

新客户端与服务端契约随同一插件包交付。旧窗口或过期编辑凭据不能绕过新写入检查；升级后提示刷新或重开。若实现中发现必须改变同步数据格式，先补方案并重新确认。

用户已明确允许实施并确认 A1 布局，随后要求连续完成 A 阶段。A1—A5 已按下列顺序完成，现统一提供结果、验证边界、体验指引及接续建议，等待用户审核。B 仍须先补齐具体方案，不在本批直接实施。

| 步骤 | 范围与交付物 | 完成门槛 | 相对工作量 |

## 7. 验证与验收清单

按[三档验证范围](../../AGENTS.md#验证范围)执行；每阶段一次完整交付检查，不因重复截图、合并或同一内容反复跑全量回归。

- **规划文档**：核对差异、相对链接和规划一致性；A1 样稿与原型另按下一条实际验证。
- **A1**：临时样稿与指定隔离宿主的专项验证，补齐未知点，不重复已完成的前期验证；区分真实能力、模拟提示和未验证点，截图不能代替数据保存证明。
- **A2**：类型检查、构建和相关布局/客户端测试，从实际入口验收。若改到保存逻辑，提升到第三档。
- **A3—A4**：涉及保存与恢复，运行类型检查、构建和全量回归；补充服务端竞争请求与真实双窗口操作，不能只测试按钮禁用。
- **A5**：内部体验包完成第三档检查、包内容核对、实际安装和指定私库同步验收；相同内容已有完整检查时复用结果，有新增改动或失败则重跑受影响检查。A—D 最终候选包的统一发布验收按主规划另行完成。

## 8. 风险、回退与交付界限

主要风险是窗口生命周期、恢复稿归属、迟到写入和布局拥挤。通过 A1 提前验证、服务端统一保护、沿用修订校验和真实宽窄界面验收控制；不扩展为协同编辑系统。

代码回退使用普通回退提交。优先关闭独立入口而保留宿主内笔记；回退前完成或明确保留未保存稿，关闭新窗口，再恢复匹配版本。本批不计划改变云端笔记格式；如本机恢复信息新增字段，保留恢复文件直到内容被确认保存，不用清缓存作为回退手段。

每步由 Agent 主动交付已实现内容、实际验证结果、操作截图、用户体验指引及接续安排；新能力只有达到该步门槛才标为完成，同时更新主规划状态。需要补充的实现细节由 Agent 提前准备，用户只参与验收及必要确认。当前已完成 A1—A5 并统一交付，用户审核体验后接续 B 的具体方案确认。
