# E 阶段：导入限制参考与常见规模小测

2026-11-10。按用户授权，在[E 整合方案](2026-11-10-stage-e-implementation.zh.md)先落盘后，查询官方说明并做有限测试。**没有修改正式源码、依赖、体积规则或安装包。** 用户随后明确：重点是图片、普通文件的单个大小、合计大小和数量；文字不是本轮重点，已做文字小测仅留作补充。不评测百万字或 GB 级材料，也不把本机结果推广为大多数电脑的结果。

## 竞品参考：先分清限制对象

| 产品与官方来源 | 当前说明 | 对肥鱼的意义 |
| --- | --- | --- |
| [Notion 导入](https://www.notion.com/help/import-data-into-notion)的 Text & Markdown 段 | 单文件免费方案 5 MB、付费方案 50 MB；支持多文件和 ZIP。 | 限制同时受套餐影响，不能证明 5/50 MB 是电脑处理性能的分界。 |
| [Obsidian 附件](https://obsidian.md/help/attachments)与 [Sync 方案](https://obsidian.md/help/sync/plans) | 附件是本地普通文件；Sync Standard 单文件 5 MB，Plus 200 MB。 | 5/200 MB 是云同步套餐限制，不是本地 Markdown 编辑或导入上限。所查本地附件说明未给统一体积上限，不据此宣称无限流畅。 |
| [Joplin 附件](https://joplinapp.org/help/apps/attachments/) | 桌面可添加各种文件；官方页面仍提示移动端不支持超过 10 MB 的资源。 | 该数字针对移动端，不能移作 Windows 桌面硬限制。未验证 Joplin 具体版本实际表现。 |
| [GitHub 普通仓库文件规则](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github) | 单文件超过 50 MiB 提醒，超过 100 MiB 拒绝。 | 是肥鱼现有同步方式的外部约束，不是正文解析或图片显示能力的证明。 |

结论：所查限制针对的对象不同，不能把具体阈值当作通用标准。参考其分类和提示方式，再检查自己的常用处理路径；不照搬收费套餐或移动端数值。表格保留来源的 MB/MiB 单位，不将两者悄悄等同。

## 当前限制盘点：单项、单篇、单批与整库分别看

| 范围 | 0.8.0 当前规则 | 来源与说明 |
| --- | --- | --- |
| 图片 | 单张 5 MiB，每篇合计 20 MiB，最多 128 张 | [常量](../../src/notes/types.ts)、[素材检查](../../src/notes/assets.ts)。字节数不能代替像素和解码内存。 |
| 普通附件 | 超过 10 MiB 确认，超过 50 MiB 拒绝；每篇最多 128 个、合计 200 MiB | [合同](../../src/contracts/notes.ts)、[内容校验](../../src/notes/validation.ts)。PDF、音频、视频等按文件保存，不预览、播放。 |
| 文件夹/ZIP 导入 | 单批合计 200 MiB、最多 10,000 项和 5,000 篇 Markdown | [前端导入](../../src/client/library-import.ts)。ZIP 计数还涉及目录项，体积包括解压后的纳入文件；不是一篇正文的限制。 |
| 笔记数据累计大小 | `notes/` 目录 512 MiB；远端笔记快照读取也限制累计 512 MiB | [文件检查](../../src/notes/files.ts)、[同步](../../src/notes/sync.ts)。包括正文、历史修订、原始素材、图片与附件等实际文件，不含仓库 `.git/`；不是 GitHub 限额。 |
| 库内笔记数量 | 最多 5,000 个保留修订的笔记 ID，含回收站和模板；笔记与笔记本修订合计最多 100,000 | [仓库检查](../../src/notes/repository.ts)。这些是当前保护值，不是性能实测结论；不是每个笔记本单独计算。 |

文字仍保留现有单篇 Markdown/正文 10 MiB 等基本校验，文件内链接不会把外部图片/附件字节算进文本。完整规则不能归结为“10 MiB 提醒、50 MiB 拒绝”；尤其整体 512 MiB 检查必须与单文件放宽一起评估，不能让用户材料选完、保存或同步时才遇到另一道限制。

## 小测方法与范围

- Windows，本机 i9-13900H、约 32 GiB 内存，Node 24.21.0，独立无界面 Chrome 156.0.8078.81，页面尺寸 1280×900；未修改浏览器安全设置，无登录或个人资料。
- 将现有前端导入源码打包到临时测试页面，产品代码未修改；每种输入顺序测 5 次，首个样本不剔除，中位数和最大值同时报告。
- 普通附件采用 1/8 MiB 合成二进制文件及一篇引用它的短文，调用真实扫描、内容转换和附件编码。附件及保存接口用替身核对字节数和附件记录；计时包含替身解码核对的开销，没有实际宿主传输、文件落盘或 Git 操作。
- 图片为一张合成的 2048×1536 JPEG，1,992,795 字节，同时解码 8 份，总计 15,942,360 字节。使用浏览器 `createImageBitmap`，不是 8 张不同照片，也不是产品阅读器显示/滚动测试；计时不含样本生成。
- 混合 ZIP 含 50 篇短文、8 份上述 JPEG、8 个各 1 MiB 的普通文件，共 66 项；ZIP 约 23.22 MiB，展开约 23.21 MiB。只测解压和扫描出待导入列表，不测逐篇转存、保存和同步。
- 同时记录界面线程的零延时回调等待时间与 Long Task；这是处理期间让出执行机会的探针，不是用户真实点击后的完整交互指标。
- 不含宿主启动、编辑器/图片实际显示、磁盘保存、GitHub 同步、进度/取消或后台继续会话的验收。没有用 CPU 降速模拟其他电脑，没有声称覆盖低配设备。

## 图片与文件结果（20 次）

| 输入/环节 | 实际规模 | 处理耗时中位数 / 最大值 | 回调等待中位数 / 最大值 |
| --- | --- | --- | --- |
| 普通附件前端准备与替身核对 | 1 个 1 MiB 文件 | 23.3 / 39.8 ms | 23.4 / 39.9 ms |
| 普通附件前端准备与替身核对 | 1 个 8 MiB 文件 | 173.4 / 177.2 ms | 173.6 / 177.3 ms |
| 浏览器 JPEG 解码 | 8 份 2048×1536 图片，单份约 1.90 MiB，合计约 15.20 MiB | 49.0 / 60.6 ms | 0.7 / 0.8 ms |
| ZIP 解压与扫描 | 50 篇、66 项，展开 24,336,008 字节 | 70.1 / 92.4 ms | 70.1 / 92.4 ms |

1 MiB 文件及异步图片解码未记录到长任务；8 MiB 文件准备最长任务约 177 ms，混合 ZIP 约 92 ms。图片解码时间与回调等待分开，不能把 60 ms 解码误称为 60 ms 界面卡死；附件编码、解压等同步工作确有短暂占用界面的情况。

这些结果支持优先做好常见材料的处理方式，没有证据要求为极端规模重建架构；也没有证明当前 5/20/50/200/512 MiB 恰好是合理边界。未测试任意格式大图、巨大像素、百 MiB 文件、库累计到 512 MiB 或数量上限，不由小样本推算这些规模的耗时。

## 附带文字与小包记录（15 次，不再扩大）

单篇含中文段落、标题、列表、表格、代码块和链接；调用真实转换，仅保存接口为替身。较早的小 ZIP 含 50 篇、1 张 9,871 字节 PNG、8 个各 1 MiB 普通文件，只测解压扫描。

| 输入/环节 | 实际规模 | 处理耗时中位数 / 最大值 | 回调等待中位数 / 最大值 |
| --- | --- | --- | --- |
| 单篇前端准备 | 10,129 字符，19,261 字节 | 37.9 / 60.2 ms | 37.9 / 60.5 ms |
| 单篇前端准备 | 50,103 字符，95,259 字节 | 197.7 / 211.6 ms | 197.8 / 211.7 ms |
| ZIP 解压与扫描 | 50 篇、59 项，展开 8,500,869 字节 | 6.7 / 12.2 ms | 6.7 / 12.2 ms |

这里的字符数包括文字、标点、空格和 Markdown 语法，不等于纯汉字数。单篇核对保存前正文内容保持；ZIP 核对篇数、文件数和扫描警告为空。

约 5 万字符样本出现最长 211 ms 的界面线程任务，作为现有转换可能重复解析的附带发现；不因此把长文本扩容列为本轮主线。普通附件包解压/扫描较快，也不说明完整导入仅需 7 ms。

本次仅发现了现有转换链路的改进理由，未证明取消、后台工作或整套导入交互已经达标；不进行无目的的重复测试或扩大压力。

## 对 E 实施的决定与修订

后续用户接受所提容量建议，但指出单次 200 MiB 封顶缺少依据，要求以进度、取消、不阻塞其他操作解决。因此撤回保留固定批次总量限制的建议；完整规则统一见 [E 实施方案](2026-11-10-stage-e-implementation.zh.md#体积与性能只围绕常见使用)。下述为规划决定，不改变上文 0.8.0 当前限制或测试覆盖范围。

1. 核心验收使用几 MB 的截图/照片和普通附件、几十项的小批次；记录单项、合计体积及数量。既有长文只抽查编辑功能，不继续探索百万字边界。
2. 最新讨论已明确多线程：ZIP 解压、较重解析/转换和编码由 Web Worker 处理；界面线程只做操作与轻量更新，文件读写使用异步分块和有限并发。不能用延迟启动主线程同步工作代替后台线程。提供当前文件、数量/总量和有效取消；收起进度或切换会话仍能继续其他工作，取消后明确哪些已完成，不建设永久任务中心。正式宿主线程加载与完整交互尚待 E2a 验证。
3. 单文件保存采用超过 50 MiB 提醒、超过 100 MiB 拒绝；正文图片预览暂定 20 MiB、3200 万像素，超出可作为普通附件保留原图。取消单篇图片/普通附件合计体积硬限，图片与普通附件各 128 个的数量保护暂保留。数值是 MVP 策略，非实测硬件极限。
4. 取消单次 200 MiB 封顶：当前 ZIP 使用界面线程同步解压并保留整个展开结果，属于实现方式问题；文件夹附件本可逐个读取，不应照搬 ZIP 内存处理的保护值。改用工作线程与逐文件/分块处理，及时释放数据；不能只把整个包搬进 Worker 继续堆积内存。现有依赖有异步/分块能力，尚未在正式入口实现验证。
5. 取消整库 512 MiB 硬限，同时改造集中读取，并统一保存、同步、导入和导出链路。约 1/5 GiB 分级提醒，资料占用与 Git 历史分别说明；不承诺不限规模流畅，不自动删除历史。库内 5,000 篇、合计 100,000 修订和单批数量保护暂保留；临近提醒，达到限制仍允许阅读、导出和清理。文字基本校验保持。
6. 正式验收除普通小批次外，选少量文件组成的略超 200 MiB 目录/ZIP，验证完成、取消、继续其他工作及内存占用；取消整库封顶也要针对性跨过旧边界。材料规模大与单文件巨大分开，不为此做百万字或 GB 级单文件专项。
