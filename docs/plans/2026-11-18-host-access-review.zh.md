# 市场合并反馈：接入 DSH HTTP 访问检查

2026-11-18。用户已授权「能够读取，就进行评估和修复」；本轮已完成，见[验证与隔离体验](2026-11-18-host-access-results.zh.md)。不发布、不向外提交市场 PR。

## 依据与判断

- 市场更新 [PR #15913](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pull/15913) 于北京时间 2026-11-17 01:20 合并。
- [维护者反馈](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pull/15913#issuecomment-6924418217)：`webServer.register` 的原始路由不自动执行 DSH 访问检查；可以在 handler 入口调用 `ctx.connection.requestRejection(req)`，或迁移到 `connection.fetch.register`。
- 当前 `src/index.ts` 确实直接注册原始 HTTP handler。`src/host/routes.ts` 已有 loopback、精确端口 Host、Origin、Fetch Metadata、方法、请求体、笔记库及窗口身份校验，因此不能将其描述为完全没有防护；但这些校验不等于 DSH 登录认证。
- 安装的官方 `@deepseek-ai/dsh-client-connection@0.2.2-rc.3` 公共类型与源码确认 `requestRejection` 返回 `401 | 403 | undefined`，执行 Host/Origin 和浏览器/API 身份校验。未接入时本机无认证请求能够到达插件业务，属于需要补齐的访问边界。

## 方案与取舍

采用维护者的入口检查方案：注册时同时依赖 `webServer` 与 `connection`，所有宿主路径先通过 `requestRejection`，再进入原 handler。拒绝请求不读取正文或执行业务，认证服务缺失时不注册，检查异常时拒绝而非放行。

完整迁移到 Fetch 路由需改 `/api` 路径、客户端和流式上传下载适配，扩大范围且没有本轮必要收益，暂不采用。

独立窗口有自己的 loopback listener，不使用 DSH HTTP 端口，也没有 DSH 浏览器登录 Cookie；本轮不将宿主认证硬套到其上。沿用其本机、同源、跨站与编辑身份限制，并验证仍可用。该入口不是 DSH 已认证接口，交付明确边界，不把「加了宿主检查」扩大成全部本地服务采用 DSH 登录。

- 增加覆盖全部路由的拒绝/放行、异常与释放测试，核对真实宿主请求与现有 fence 仍有效；构建更新 `lib/`。

## 风险与回退

- Electron 的请求转发及浏览器资源下载必须带宿主认证，实际验收确认，不能仅测试模拟 header。若发现不兼容，先核对公共转发机制，不通过绕过检查修复。
- 依赖未就绪/宿主热重载时旧路由须撤销，避免认证检查被绕过。
- 回退以本轮基线 `d39404c` 构建内部候选或新增回退提交；不移动发布标签、不重写历史，隔离安装前保留旧插件副本。
